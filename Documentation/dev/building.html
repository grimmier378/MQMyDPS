Building

Prerequisites

  • MacroQuest source tree (provides MQ2Main, eqlib, ImGui, ImPlot, fmt, Blech, and the protobuf + abseil libraries)
  • Visual Studio with the C++ toolset and MSBuild (this dev machine uses VS 2026 Insiders / v18; any recent VS that builds the MQ solution works)
  • Win32 (x86) platform — EverQuest is a 32-bit process

Setup

  1. Clone or place the MQMyDPS folder under plugins/ in your MacroQuest source tree
  2. Add MQMyDPS.vcxproj to the MacroQuest Visual Studio solution
  3. Ensure the Win32 (x86) platform configuration is selected

Build Command

"C:\Program Files\Microsoft Visual Studio\18\Insiders\MSBuild\Current\Bin\MSBuild.exe" D:\gitStuff\macroquest\plugins\MQMyDPS\MQMyDPS.vcxproj -p:Configuration=Release -p:Platform=Win32 -nologo -verbosity:minimal

The MSBuild path is install-specific. If it differs on your machine, locate it with vswhere or search under C:\Program Files\Microsoft Visual Studio\.

Output

Builds as a DLL. Place in the MQ plugins directory. Load with:

/plugin MQMyDPS

Cross-Client / 64-bit (EMU vs LIVE)

The default build targets the EMU client (32-bit, Win32) — that is the client the author plays. The same source also builds for the LIVE client (64-bit, x64); the .vcxproj already carries both Win32 and x64 configurations.

Build identity comes from eqlib/BuildType.h, which is selected by the eqlib branch you build against:

MacroMeaning
IS_EMU_CLIENT / IS_LIVE_CLIENT / IS_TEST_CLIENTWhich client family this build targets
IS_EXPANSION_LEVEL(x) / IS_CLIENT_DATE(x)Feature gating by expansion / client date
HAS_DIRECTX_11 / HAS_DIRECTX_9Renderer backend (EMU/RoF2 is DX9; recent LIVE is DX11)

BuildType.h enforces the platform: Win32 is required for EMU, x64 for LIVE. To produce a LIVE build, point the eqlib submodule at the live branch and build the x64 configuration against your live MacroQuest tree.

A cross-client audit found the plugin's eqlib surface is almost entirely common between the emu-rof2 and live branches — spawn fields (PetID, MasterID, WhoFollowing, AvatarHeight, Type), casting/spell data (LaunchSpellData, EQ_Spell::SpellIcon, IsDoTSpell()), combat state, and the graphics/camera/bone/render interfaces all match. Two points were addressed for LIVE:
  • Bone accessors take EBones on EMU but int on LIVE (GetBoneByIndex / GetBoneWorldPosition). MyDPSFloatingText.h selects the parameter type with #if IS_EMU_CLIENT.
  • FCT world-to-screen projection uses the hand-rolled worldToEye matrix math (reading CCamera fields by name). This is cross-client because the CCamera field names are identical on EMU and LIVE (only the offsets differ), and it is the same approach the community MQNameplates plugin uses. The built-in CCameraInterface::ProjectWorldCoordinatesToScreen() was tried but produced no usable screen coordinates (FCT stopped rendering), so it was reverted.

For any future client-specific divergence, gate it on the BuildType.h macros (IS_EMU_CLIENT / IS_LIVE_CLIENT or the HAS_* feature flags) rather than on raw _M_X64 checks.

Testing

No automated test suite. All testing is manual in-game. Load the plugin, engage mobs, verify damage tracking, healing tracking, FCT positioning, graph rendering, and MQMyChat output.

Troubleshooting

  • If the plugin fails to load, check that it was built for Win32 (x86), not x64
  • If FCT doesn't appear, verify showFCT is enabled in settings and that you have a valid target
  • If MQMyChat integration doesn't work, verify MQMyChat is loaded first: /plugin MQMyChat
