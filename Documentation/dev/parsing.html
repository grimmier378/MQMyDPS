Pattern Engine

The Problem

EverQuest sends combat and healing events as formatted chat text. There is no structured damage API, no event system with typed fields, and no spawn IDs in messages. The pattern engine must convert raw text lines into DamageRecord structs with extracted target names, damage values, spell names, and damage types.

Why Blech?

The original parser used string_view::find() with 15 hardcoded TryParse* methods. While fast, it was rigid: every EQ message format change required a code change and recompile. The replacement uses MQ's Blech B-tree pattern matching library, which provides:

  • User-editable patterns: Patterns are stored in per-server JSON files and can be edited in-game via the Patterns tab or by editing the JSON directly
  • Named captures: Blech's #name# syntax extracts substrings by name (e.g., #target#, #damage#, #verb#)
  • Wildcard matching: #*# matches any text (used for crit/deadly strike patterns with variable prefix text)
  • B-tree efficiency: Blech builds a prefix tree from all registered patterns, so adding more patterns has minimal performance cost
  • Hot reload: /mydps patterns reload re-reads patterns from disk without restarting the plugin

Blech Pattern Syntax

Blech uses # as the capture delimiter and | as the variable delimiter (neither is used in EQ chat text). Pattern syntax:

SyntaxMeaningExample
#name#Named capture: matches any text and stores it as name#target# captures the target name
#*#Wildcard: matches any text, value discarded#*#You score a critical hit!#*#
literal textMust match exactlyYou , for , points of damage.
Trailing literal requirement: Blech requires the last literal node in a pattern to consume all remaining input text for the callback to fire. If a chat line ends with "points of damage." then the pattern must also end with "points of damage." (including the period). Missing the trailing period will cause the pattern to silently fail to match.

Token Substitution

Patterns in the JSON file can contain two substitution tokens that are replaced at registration time:

TokenReplaced WithUsed In
{CharName}Current character name (e.g., "Grimmier")non_melee, deadly_strike patterns
{PetName}Current pet's DisplayedNamepet_melee, pet_non_melee patterns

Substitution happens in RegisterEvents() and RegisterPetEvents() via SubstituteToken(). The raw pattern (with tokens) is preserved in PatternDef::rawPattern; the substituted version goes into PatternDef::pattern and is registered with Blech.

Each pattern key maps to a builder function via m_builders (initialized in InitBuilders()). When Blech matches a pattern, HandleMatch() looks up the builder by key and calls it with a fresh DamageRecord and the linked list of captured values.

Value Extraction

GetBlechValue() walks the PBLECHVALUE linked list to find a named capture by string comparison. GetBlechInt() wraps this with std::from_chars for numeric conversion (returns 0 on failure).

JSON Format

Patterns are stored at [MQ Config Dir]/MQMyDPS/[ServerName]/Patterns.json. The file uses nlohmann/json (v3.12.0, header-only json.hpp).

{
    "version": 2,
    "patterns": {
        "melee": {
            "type": "Melee",
            "pattern": "You #verb# #target# for #damage# points of damage.",
            "enabled": true
        },
        "non_melee": {
            "type": "NonMelee",
            "pattern": "{CharName} hit #target# for #damage# points of non-melee damage.",
            "enabled": true
        }
    },
    "pet_patterns": {
        "pet_melee": {
            "type": "PetMelee",
            "pattern": "{PetName} #verb# #target# for #damage# points of damage.",
            "enabled": true
        }
    }
}

Version Migration

The file includes a "version" field (currently PATTERNS_VERSION = 2). When LoadPatterns() reads a file with a version lower than the current constant, it regenerates defaults and overwrites the file. This auto-upgrades patterns when the plugin ships new default patterns (e.g., the v1-to-v2 migration fixed patterns that were missing trailing periods).

Dynamic Pet Registration

Pet patterns use the {PetName} token, which changes whenever the player summons, loses, or changes pets. The engine handles this dynamically:

  1. ProcessChat() checks the player's pet on every call
  2. If the pet name changes, it calls UnregisterPetEvents() followed by RegisterPetEvents(newName)
  3. RegisterPetEvents() substitutes {PetName} in each pet pattern and registers new Blech events
  4. If the pet is dismissed or dies, UnregisterPetEvents() removes the Blech events and clears m_petName

First-match-wins

HandleMatch() sets m_matched = true on the first callback. Blech may fire multiple callbacks for a single Feed() call if multiple patterns match the same line, but only the first match produces a record. This mirrors the sequential try-and-return behavior of the old parser.

Filtering in ProcessChat

After the pattern engine returns a DamageRecord, ProcessChat() applies settings-based filters before passing to RecordDamage:

SettingFilters DamageType
showMyMissesMiss (only when isMiss is true)
showMissMeMissedMe
showHitMeHitBy, HitByNonMelee
showCritHealsCritHeal
showDSDamageShield

DirectHeal is never filtered — heals are always recorded when tracking is active.

Tip: Keeping filters in the engine rather than the pattern engine means the pattern engine is a pure text-to-structure converter with no dependencies on settings or game state. The pattern engine could be reused in test harnesses or log file readers without any MQ dependencies beyond DamageRecord and Blech.

In-Game Editing

The Config window's Patterns tab exposes all patterns as myui::StyledEditField cells — a readonly display of the current pattern that, when clicked, opens a cursor-anchored Accept/Cancel popup to edit the raw text (applied only on accept). Users can enable/disable individual patterns, edit the pattern text, save changes to disk, or reload from disk. Changes to raw patterns take effect after Save + Reload (the Blech events must be re-registered with updated text).
