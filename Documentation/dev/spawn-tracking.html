Spawn ID Tracking

The Problem

EQ chat identifies targets by name only. A damage message says "You slash a gnoll for 150 points of damage" but never tells you which gnoll. In a camp with three gnolls of the same name, all damage would be merged into a single entry without spawn ID resolution. The plugin needs unique per-mob attribution for accurate per-target DPS breakdowns.

Resolution Chain

ResolveSpawnID (MQMyDPS.cpp:1038) tries strategies in priority order, returning the first match. The chain is designed so that the most reliable and fastest checks run first, with progressively more speculative methods as fallbacks.

# Strategy Applies To How It Works
1 Empty name → synthetic ID All types If record.targetName is empty, immediately returns --m_syntheticIDCounter (a negative ID). This handles Crit/CritHeal records that arrive without a target name.
2 pTarget match Melee, NonMelee, Crit Compares pTarget->DisplayedName to record.targetName. If they match, returns pTarget->SpawnID. This is the fastest and most reliable strategy for direct combat — the player's current target is almost always the mob they are hitting.
3 Pet target PetMelee, PetNonMelee Gets the player's pet via pLocalPlayer->PetID, then checks pPet->WhoFollowing (the pet's current target). If the pet's target name matches, returns its spawn ID. Pets have their own target independent of the player.
4 DoT registry DoT Calls ResolveDoTSpawnID (MQMyDPS.cpp:1109) which searches activeDoTs for an entry matching both targetName and spellName. If the spell name is empty, matches on target name alone. Falls through to pTarget check if no DoT match found.
5 currentTargets cache All types (fallback) Linear scan of the per-battle currentTargets map. If any existing entry has a matching name, returns its spawn ID. This prevents re-resolution when the same mob is hit repeatedly — once resolved, the ID is reused.
6 XTarget scan All types (fallback) Calls ResolveFromXTarget (MQMyDPS.cpp:1121). Scans the extended target list with strict filters: non-empty slots, matching name, SPAWN_NPC type only, excludes player pets (MasterID check verifies the master is not a player). Only returns a match if exactly one candidate is found.
7 Synthetic fallback All types (last resort) Returns --m_syntheticIDCounter. Synthetic IDs are always negative, so they never collide with real spawn IDs (which are positive). Each unresolvable target gets its own unique negative ID.

Why This Order?

The strategies are ordered by reliability and specificity:

  • pTarget (strategy 2) is fastest — a single pointer dereference and string comparison. It is also the most reliable for direct melee/spell hits because the player must have the mob targeted to attack it.
  • Pet target (strategy 3) is needed because pets have their own target. The player might be targeting mob A while the pet attacks mob B.
  • DoT registry (strategy 4) handles asynchronous tick arrival. A DoT tick message arrives seconds after the spell was cast, and the player may have changed targets. The registry maps spell+target to the spawn ID recorded at cast time. Falls through to pTarget as a secondary check for DoTs since the caster may still be targeting the same mob.
  • currentTargets (strategy 5) prevents re-resolution overhead. Once a mob has been resolved by any earlier strategy, subsequent hits reuse the cached ID without needing to check targets or XTarget lists.
  • XTarget (strategy 6) is the most conservative strategy. It deliberately requires exactly 1 match to avoid ambiguity. If two gnolls with the same name are on the XTarget list, it falls through rather than guessing.
  • Synthetic (strategy 7) is the last resort. A synthetic ID keeps the target's damage separate from all other targets, even if the name matches another mob. This is better than merging damage with a wrong target.
Warning: A wrong spawn ID is worse than a synthetic one. Wrong IDs merge damage from different mobs, corrupting both targets' DPS calculations. Strategy 6 (XTarget) deliberately falls through on ambiguous names — two mobs with the same name on XTarget means neither can be reliably identified, so a synthetic ID is safer.

DoT Cast Tracking

TrackDoTCasting (MQMyDPS.cpp:1170) runs every 250ms in OnPulse. It monitors the player's CastingData.SpellID for state transitions:

Cast Detection

  1. Casting in progress (SpellID != -1): Records m_lastCastSpellID, m_lastCastTargetID, and m_lastCastSpellIcon from the current casting data.
  2. Cast completed (SpellID == -1 after being non--1): Checks if the last cast spell is both a DoT (IsDoTSpell()) and detrimental (IsDetrimentalSpell()). If so, looks up the target spawn by m_lastCastTargetID and creates an ActiveDoT entry with the target's spawn ID, displayed name, spell name, spell icon, and current timestamp.
  3. Reset: After processing, m_lastCastSpellID is reset to -1 and m_lastCastTargetID to 0.

Cleanup

Active DoTs are cleaned up through three mechanisms:

  • OnRemoveSpawn: When a mob despawns, RemoveActiveDoTs(pSpawn->SpawnID) removes all DoT entries for that spawn ID.
  • OnBeginZone: Clears the entire activeDoTs vector on zone transitions.
  • 5-minute expiry: TrackDoTCasting runs erase(remove_if(...)) at the end of every call, removing any entry older than 5 minutes. This catches DoTs on mobs that expired or were dispelled without a despawn event.
Player casts Venom of the Snake on Gnoll #47 | | OnPulse: SpellID = 1234, TargetID = 47 | Records m_lastCastSpellID=1234, m_lastCastTargetID=47 v Cast completes (SpellID returns to -1) | | OnPulse: IsDoTSpell(1234) && IsDetrimentalSpell(1234) = true | GetSpawnByID(47) -> "a gnoll" | Pushes ActiveDoT{targetSpawnID=47, targetName="a gnoll", | spellName="Venom of the Snake", ...} v Tick arrives: "A gnoll has taken 300 damage from your Venom of the Snake." | | PatternEngine: BuildDoT -> targetName="A gnoll", spellName="Venom of the Snake" | ResolveSpawnID -> ResolveDoTSpawnID("A gnoll", "Venom of the Snake") | Finds match in activeDoTs -> returns 47 v Damage attributed to spawn #47

Crit Path Target Initialization

Note: When a Crit or DeadlyStrike record arrives, it has no target name in the chat message itself (e.g., "You score a critical hit! (2500)"). RecordDamage (MQMyDPS.cpp:642) fills in the target name from pTarget->DisplayedName if available. If a Crit is the first hit on a new spawn ID, it initializes the target entry in currentTargets with the name, spawn ID, and firstHit timestamp. Without this initialization, the Targets tab would show blank entries for mobs whose first recorded hit was a crit.

The crit path also updates critDamage on the target entry separately from totalDamage. This is because crit damage is reported as the total hit value (melee + crit bonus combined), so it is tracked in its own accumulator to avoid double-counting in breakdown displays.
